## Configure line (planned) and what each flag does

The flag names and defaults below come from `configure --help` and `configure.ac` of 47.

| flag | 47 default | effect |
|---|---|---|
| `--disable-debug` | debug off ("default is without -g") | no `-g`, no `NGDEBUG` |
| `--with-x=no` | auto | no X11 `plot` window; also drops `frontend/help` (`if !NO_X` in `src/Makefile.am`) |
| `--with-readline=no` | yes | no GNU readline (GPL) |
| `--with-editline=no` | no | already off |
| `--disable-openmp` | on | no OpenMP. In native 47's `config.h` this is `USE_OMP 1`; it only parallelises BSIM-type device evaluation |
| `--disable-xspice` | on | no code models, no `codemodel`, no dlopen; keeps out `xspice/icm/table` (GPLv2+) |
| `--disable-osdi` | on | no OpenVAF/Verilog-A `.osdi` loading (dlopen; `src/osdi` is MPL-2.0) |
| `--disable-klu` | yes ("Default=yes") | KLU (LGPLv2) left out. Sparse 1.3 (MIT-like) remains and is the solver both native builds actually used ("Using SPARSE 1.3 as Direct Linear Solver") |
| `--with-fftw3=no` | yes | uses the built-in FFT instead of libfftw3 (GPL) |
| CIDER | off (`--enable-cider` to turn on) | stays off |
| `CFLAGS=-O2` (or `-Oz`) | | `configure.ac` line 40: `ext_CFLAGS="${CFLAGS+yes}"`. Only when CFLAGS is unset does it use `-O2 -s -Wall ...` (lines 320–340), which would give emcc a bare `-s`. EEcircuit instead seds `-Wno-unused-but-set-variable`. |

## Link flags (planned)

```
-O2 (or -Oz) -s MODULARIZE=1 -s EXPORT_ES6=1 -s EXPORT_NAME=createNgspice
-s ENVIRONMENT=web,worker,node -s INVOKE_RUN=0 -s ALLOW_MEMORY_GROWTH=1 -s FORCE_FILESYSTEM=1
-s EXPORTED_RUNTIME_METHODS=callMain,FS,ENV -s STACK_SIZE=4MB
```

- They are appended to the libtool link line of the `ngspice` program by sed on
  `build/src/Makefile`, ending with `-o ngspice.mjs`. This is the same mechanism as
  EEcircuit's `run.sh`.
- The target text `$(ngspice_LDADD) $(LIBS)` exists in `src/Makefile.in:1056`.
- No ASYNCIFY and no `control.c` patch (see below).
- emcc 7.0.0 accepted exactly these settings (in `-sNAME=VALUE` form) when I compiled the
  stand-in. The space-separated form the script uses through libtool is the one EEcircuit uses.

## Batch mode needs no ASYNCIFY (source evidence; ngspice runtime not tested)

- `src/main.c` (47), lines 1533–1588: with `-b` and `-r`, ngspice calls
  `ft_dorun(ft_rawfile)`, then `ft_cktcoms(TRUE)`, then `sp_shutdown(EXIT_NORMAL)`, which
  calls `exit()` (line 557).
- The interactive loop `while (cp_evloop(NULL) == 1)` (line 730) is never reached. That loop is
  what EEcircuit and wokwi patch (`getcommand` in `control.c`) and why they need ASYNCIFY.
- Batch mode uses `SETJMP(jbuf, 1)` (line 1539), which Emscripten's default `SUPPORT_LONGJMP`
  handles.
- Stand-in check, `$S/wasm/standin/standin.c`. This is not ngspice: it reads the netlist,
  writes a 2-plot binary rawfile and ends with `exit(0)`. Built with the flags above (no
  ASYNCIFY):
  - `callMain(['-b','-r','/out.raw','/circuit.cir'])` returns 0 synchronously.
  - print/printErr are captured.
  - `/out.raw` is read back and parsed (two plots).

## callMain more than once, or a fresh instance per run

- Stand-in, `--reuse` mode: `exit(0)` inside `callMain` leaves the runtime usable
  (EXIT_RUNTIME=0 is the default), and three consecutive `callMain` calls on one instance
  all succeeded.
- **But C globals persist**: the stand-in's static counter went 1 → 2 → 3, and its init-once
  pointer stayed set.
- ngspice keeps its circuit list, plots and variables in globals, and its `cp_*` init runs from
  `main`. Reusing an instance therefore carries state from run to run.
- Whether ngspice still gives correct results that way can only be tested on the real build.
  The harness's `--reuse` mode does that comparison.
- **Default: one compiled `WebAssembly.Module`, a fresh instance per run**, via
  `instantiateWasm` (implemented in the harness).
- Stand-in timings (16 KB wasm): compile 0.56 ms, instantiate 1.9–6.0 ms, run 0.1–2.6 ms.
  ngspice's numbers will be larger because its data segment and memory are bigger.
  **They have not been measured.**

## spinit

- Source (47):
  - `src/misc/ivars.c:64–75`: `Spice_Lib_Dir` = `NGSPICEDATADIR` (`configure.ac:1003`:
    `$dprefix/share/ngspice`, so `/usr/local/share/ngspice` by default). It is overridden by
    `SPICE_LIB_DIR`.
  - The spinit directory is `Lib_Path` = `$Spice_Lib_Dir/scripts`, overridden by `SPICE_SCRIPTS`.
  - `src/frontend/cpitf.c:249–325`: tries `<Lib_Path>/spinit`; if it is absent, prints
    `Warning: can't find the initialization file spinit.` on stderr and continues.
- Runtime check, from `$S/wasm/results/spinit-test` with `SPICE_SCRIPTS` pointing at an empty
  directory, running F1a:
  - native 42: stderr `Note: can't find the initialization file spinit.`, exit 0,
    `v(n1) = 6.0000000000000000`.
  - native 47: stderr `Warning: can't find the initialization file spinit.`, exit 0, same values.
- With XSPICE and OSDI off, the stock spinit (`src/spinit.in`) does nothing that affects batch
  numerics. It sets two aliases, `x11lineararcs` and `num_threads`, unsets `osdi_enabled`, and
  its codemodel/osdi blocks are skipped.
- **So the wasm build needs no spinit.** For a clean stderr, the harness writes a 3-line spinit
  (aliases only) to MEMFS at `/usr/local/share/ngspice/scripts/spinit` before `callMain`.
  - Setting `ENV.SPICE_SCRIPTS` instead only works from `preRun`, because Emscripten builds
    `environ` in a constructor before the factory's promise resolves.
- In the shared library, `ngSpice_nospinit()` skips spinit entirely.

## Shared library or batch executable

- **Batch executable (preferred).**
  - It is the same code path as the native CLI the golden tests compare against
    (`ngspice -b -r`).
  - No ASYNCIFY.
  - Isolation comes from a fresh instance per run.
  - The output contract is the rawfile, about 100 lines of parser, already tested on 42 and 47.
  - Limits:
    - `.meas` is skipped with `-r`; use a `.control` block with `run` / `write` / `meas`
      instead (tested on native 42).
    - Results arrive only at the end of a run (no progress callbacks).
    - It costs one instantiate per run.
- **Shared library** (`--with-ngshared`; API in `src/include/ngspice/sharedspice.h`:
  `ngSpice_Init`, `ngSpice_Circ`, `ngSpice_Command`, `ngGet_Vec_Info`, `ngSpice_AllVecs`,
  `ngSpice_Reset`, `ngSpice_nospinit`).
  - Gains:
    - vectors read straight from wasm memory, no rawfile;
    - a persistent session (`alter`, re-run);
    - `.meas` works;
    - SendData/SendStat progress callbacks.
  - Costs:
    - libtool would try to build a `.so`, so the convenience libraries plus `sharedspice.o`
      would have to be linked into a main module by hand, with `EXPORTED_FUNCTIONS`
      (`_ngSpice_Init`, etc.) and JS callbacks through `addFunction` (`ALLOW_TABLE_GROWTH`);
    - `bg_run` needs pthreads (`sharedspice.c:88–120`), which in a browser means
      SharedArrayBuffer and COOP/COEP headers that GitHub Pages cannot set, so only the
      synchronous `run` is usable;
    - `src/Makefile.am:593` adds `-lstdc++` to `libngspice_la_LDFLAGS` unconditionally.
  - It is more glue, and it moves away from "same as the CLI".
- **Verdict:** start with the batch executable. Move to the shared library only if persistent
  sessions or streaming are needed.
